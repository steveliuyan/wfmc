# 在新对话里接着干 WFMC（一页说明）

> 写给"下一个对话里的我"和"我自己"。看一眼就知道：新开一个对话要怎么起步、每次干完要回写什么、上下文太长时怎么交接。
> 最后更新：2026-11-09（1.3.1 发布当天）。

---

## 0. 为什么要这份文件

WFMC 这个项目现在的体量：主进程 43 个模块 / 渲染层 12 个页面 + 10 个组件 / 约 16k 行，加上 40 多个版本的发版史。**任何单个对话都装不下全部上下文**，而新对话里我没有旧记忆。

所以交接不靠"把聊天记录带过去"，靠**仓库里的文档**：

| 文件 | 什么时候读它 | 什么时候改它 |
|---|---|---|
| `HANDOFF.md` | 动手改代码前（尤其 §13 坑清单、§14.x 最近几节） | 每次改完架构/踩坑层面的事，追加一节 §14.NN |
| `docs\项目交接.md` | 只管"跑起来 / 打包 / 发版 / 删旧版本"时 | 发版流程变了才改 |
| `docs\新对话接手.md`（本文） | 新对话第一件事 | 起步流程变了才改 |
| `CHANGELOG.md` | 写发版说明时 | 每次发版，顶部加一节（用户能感知的变化） |
| `AGENTS.md` | 想知道编码/构建约定时 | 约定变了才改 |
| `docs\服务端交接.md` | 碰服务端那半边时 | 同上 |

**一句话**：这套项目文档就是"跨对话的长期记忆"，代码改了文档不改，下个对话就等着重新踩坑。

## 1. 新对话开工三步（5 分钟）

### 第一步：把这句话发给它（可直接复制）

```
项目在 H:\mcqidongqi（WFMC · 万凡 Minecraft 启动器，Electron 38 + React 19 + TS + Vite）。
先按顺序读：
1) docs\新对话接手.md
2) HANDOFF.md 的 §0 一页速览 + 最后两节（§14.13 / §14.14）
3) AGENTS.md 的构建与约定部分
读完先别改代码，用三句话说清：当前版本、最近一版改了什么、我这次要做的事在代码里的落点文件。
```

### 第二步：给它"这次要做什么"和"不许动什么"

- 要做的事：一句话 + 现象（有截图就贴图）。
- 不许动的（照抄进第一条消息，能省掉一半返工）：
  - 不改架构：仍然 `ipcMain.handle('<域>:<动作>')` ↔ `window.launcher.invoke(...)`。
  - 不动 `build\installer.nsh`（`customRemoveFiles` 是拦"更新时删整个安装目录"的）。
  - 不把数据目录挪进安装目录。
  - 渲染层不能 `import` 主进程模块（类型要在 `src/renderer/api.ts` 里自己声明一份）。
  - 改 `package.json` 必须无 BOM（用 Node/`[IO.File]::WriteAllText`，别用 `Set-Content -Encoding utf8`）。
  - **这台机器没有 git / gh CLI**：发版走 `scripts\publish-github.mjs` + `.local\gh-token.txt`，源码同步走 `scripts\opensource.mjs`。

### 第三步：让它先读落点，再动手

标准三件套：`src/main/ipc.ts`（能力全表）→ `src/shared/types.ts`（数据结构）→ `src/renderer/api.ts`（前端怎么调）。
然后才看具体那个页面/模块。

## 2. 干完一件事，回来写什么（照抄）

### 2.1 必做：三处

1. **`HANDOFF.md` 追加一节 `§14.NN`**，按「现象 → 真因 → 改法 → 怎么验」写。真因要写**为什么会出现**，不是"我改了哪几行"。这次的样板见 §14.14（四个报障的根因）。
2. **`CHANGELOG.md` 顶部加一节**，只写用户能感知的变化（不写"重构了 xx 函数"）。
3. **`package.json` 版本号 +1**（小修 `1.3.x`，新功能 `1.x.0`）。

### 2.2 发版（4 条命令，别跳）

```powershell
cd H:\mcqidongqi
npm run typecheck                    # 必须 0 error
npm run i18n:check                   # 必须 100%（加了中文文案就得配英文，否则 CI 红）
npm run build
npx electron-builder --win --x64     # 出 release\WFMC-{Portable,Setup}-<ver>.exe
$env:GH_TOKEN=(Get-Content .local\gh-token.txt -Raw).Trim()
node scripts\publish-github.mjs --owner steveliuyan --repo wfmc --tag v<ver> --notes "docs\更新说明-<ver>.md"
node scripts\cleanup-releases.mjs --owner steveliuyan --repo wfmc --keep v<ver> --dry   # 先看
node scripts\cleanup-releases.mjs --owner steveliuyan --repo wfmc --keep v<ver>         # 真删
```

`--notes` 建议单独写一份 `docs\更新说明-<ver>.md`（只放这一版），别直接把整个 `CHANGELOG.md` 当 release 说明——历史会一起贴上去。

### 2.3 判断对错（"我干的这些对不对"要留证据）

写进 §14.NN 的「怎么验」里，三选一或全上：

- **真实数据跑一遍**：例如体检用真实实例（`F:\wfmc-data\instances\create-delight-remake`，369 个 jar）离线跑 `diagnoseMods`，11 条 → 0 条。
- **真实主进程验证**：账号类改动要用 electron 真跑（假环境的 `safeStorage` 行为不一样）。
- **自动化卡口**：`npm run typecheck` / `npm run i18n:check` / `npm run test:core` / `npm run smoke`。

## 3. 上下文太长怎么办（这次的实际情况）

现象：单个对话做到后面，"我记得的东西"已经超出模型能稳定记住的量，我会开始重复解释项目结构、忘记前面定下的约束。

做法（按推荐顺序）：

1. **一个对话只干一件事**。一个报障/一个功能 → 修完 → 发版 → 回写文档 → **开新对话**。不要在一个对话里连做三个不相干的报障。
2. **新对话第一句只给"路径 + 一句话任务"**，不要贴大段代码或聊天记录。让它自己读文件——读文件是便宜的，贴进对话的旧记录是贵的，而且会挤掉它读新文件的空间。
3. **跨对话的"我正在改什么"写进文件，不靠聊天记忆**。用下面这个模板（要连做多步时，开一个 `docs\当前进度.md`）：

```markdown
# 当前进度（YYYY-MM-DD）
- 在做：<一句话>
- 已完成：<哪些文件、哪些行为可验证>
- 卡在哪：<具体卡点 + 已经排除的可能>
- 下一步：<下一件要做的事>
- 别动：<这次明确不许碰的东西>
```

4. **同一件事反复改不好，就换对话重开**：把 `docs\当前进度.md` 交给新对话，比起在一个已经跑偏的长对话里继续打补丁更快。
5. 如果只是"想知道上次改了什么"，先读 `CHANGELOG.md` 顶部两节 + `HANDOFF.md` 最后两节，不用问人。
